# Command and local HTTP interfaces
Run `build/stockguard --db PATH [--policy config/policy.json]`. Input and output are JSON lines.
Each request is an object with `op`. Response is `{"ok":true,"result":...}` or
`{"ok":false,"error":"code","message":"explanation"}`. Exit code 0 means every request
succeeded, 1 means at least one request failed, 2 means startup or invocation failure.
A partial batch has a successful envelope with independent per-item `ok` fields.

Limits: 1 MiB per line, 64 JSON nesting levels, 16 KiB observation, 128-byte ASCII IDs,
4096-byte metadata object, 1000 observations per batch, 1000 query rows per page.
Query commands accept `limit` (1 to 1000) and `offset` (nonnegative). Pagination is a
transactional snapshot per page, not a consistent snapshot across a changing multi-page query.
All timestamps are Unix seconds. Inventory and decision clocks are generated by the service.

| op | Required request fields |
| --- | --- |
| product_put | id, name, category, unit, status (active or inactive), optional metadata |
| products | optional id, limit, offset |
| initialize | product_id, location_id, quantity, actor |
| inventory | optional limit, offset |
| ingest | observation object |
| batch | batch_id, observations array |
| movement | id, product_id, location_id, delta, expected_version, actor |
| review | observation_id, actor, action; expected_version and verified_at for confirm/correct; quantity for correct |
| pending | optional limit, offset; includes unresolved REVIEW and DEFER |
| history | optional limit, offset; immutable original decisions |
| reviews | optional limit, offset; terminal review actions |
| audit | optional limit, offset |
| metrics | no extra fields |

Observation fields: id, scan_id, product_id, location_id, quantity, confidence (finite 0 to 1),
observed_at, expected_version, complete (boolean), source, optional model_version and metadata.
Unknown fields are retained in replay payload comparison but do not influence policy.
A repeated ID with the same canonical parsed JSON returns the saved original decision with
replayed=true, even after review or a policy change. Different JSON values conflict. Changing
field order does not conflict; adding optional fields or changing numeric representation may.
Alternate IDs with the same scan key are persisted as REJECT duplicate_scan. A deferred
observation can be manually verified after prerequisites exist, or replaced by a new scan ID.

Rejection closes pending evidence without changing inventory or adding an inventory audit.
It needs no active product, inventory record or expected_version. Its result reports current
quantity/version when inventory exists, otherwise both are null. Confirmations and corrections
still require an active product, existing inventory, matching version and fresh verification.

The loopback dashboard serves `POST /api` with the same request/response schema,
`GET /health`, `GET /benchmarks`, and fixed static assets. It runs at most 8 active handlers
and gives backend calls 15 seconds. Backend validation failures use HTTP 400, adapter failures
503. GET health actually queries C++/SQLite. Browser actions show original reasons and evidence.
Host and Origin checks prevent DNS rebinding and cross-site writes. JSON Content-Type is
required. The interface is a local demonstration, not a production authenticated API.
Review actor strings are synthetic attribution, not cryptographic identity or authorization.
Do not expose it on a public network. Database file access is the local trust boundary.
