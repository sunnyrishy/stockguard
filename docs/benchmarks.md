# Benchmark methodology and measured results

Executed October 11, 2026, GCC 14.2, Release (-O3 -DNDEBUG), SQLite 3.54.0.
Hardware: AMD EPYC 9V74 80-Core Processor, 5 CPUs available to the container.
The database is on /tmp tmpfs in this runner. FULL synchronous remains enabled, but
tmpfs does not represent physical durable storage or repository-workspace I/O latency.

## Durable service throughput

The C++ Store benchmark includes JSON request construction, validation, prepared statements,
policy evidence, a separate transaction per observation, inventory update and audit insertion.
It excludes CLI process startup, HTTP, dataset generation, connection startup and final replay
checks. Workers operate on separate inventory locations in the same database. SQLite remains
one writer. Median/P95/P99 cover each operation, including observed writer wait. A final ledger
invariant verifies exactly N version advances and unchanged quantity 100. Each run also checks
100 durable replayed IDs without an extra version increment.

| Observations | Workers | Observations/s | Median us | P95 us | P99 us | Peak RSS KiB |
| --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 1 | 9,729.8 | 88.3 | 134.2 | 252.2 | 10,368 |
| 10,000 | 1 | 7,951.5 | 104.9 | 169.1 | 383.9 | 10,624 |
| 100,000 | 1 | 7,244.1 | 120.3 | 195.3 | 418.8 | 37,772 |
| 10,000 | 2 | 6,409.1 | 120.8 | 230.6 | 462.1 | 11,320 |
| 10,000 | 4 | 7,236.3 | 87.4 | 195.2 | 512.1 | 15,884 |

Peak RSS includes the labeled dataset retained by the harness, not just the engine. Database
bytes are measured while connections are open and exclude active WAL/SHM sidecars. These are
single runs, without confidence intervals. More workers did not consistently improve throughput;
the measurements do not justify an asynchronous worker queue. No performance target or
unsupported speedup claim is asserted.

## Labeled correctness comparison

Seed 2026, std::mt19937, 10 equally likely scenario slots, each a fresh independent ledger
at count 100 and version 1. Incorrect cases are large high-confidence count, low-confidence
zero count, partial count, stale count and a plausible wrong count of 102. A correct count
with low confidence deliberately produces false positives. Other slots are correct counts.
The exact scenario distribution and counters are generated by executed code.

A positive means gated for review, recount or rejection, not necessarily human review alone.
Blind acceptance accepts every formatted count. Confidence gates at 0.95. Verify everything
gates all counts with a perfect simulated human verifier. StockGuard combines confidence,
coverage, version, freshness and discrepancy. Incorrect count means quantity differs from
synthetic ground truth, not violation of a database invariant.

| Policy | Incorrect committed | Gated workload | Precision | Recall |
| --- | --- | --- | --- | --- |
| blind | 5,070 | 0 / 10,000 | 0.00% | 0.00% |
| confidence | 4,006 | 2,055 / 10,000 | 51.78% | 20.99% |
| stockguard | 1,039 | 5,022 / 10,000 | 80.27% | 79.51% |
| verify_everything | 0 | 10,000 / 10,000 | 50.70% | 100.00% |

StockGuard gates 4,031 of 5,070 incorrect counts, but commits 1,039 plausible wrong counts.
It gates 991 correct low-confidence counts too. This is a policy demonstration with an
intentionally difficult false-negative case, not evidence of real-store accuracy. The perfect
verification baseline has no wrong updates by assumption, not by an implemented human model.
The assumed verification cost is 15 seconds per gated count. That is a cost model, not measured
labor. Rejected/deferred items incur a modeled recount cost for comparison.

The separate policy_timings in the JSON reports evaluate already parsed observations. Simple
baselines return a boolean, whereas StockGuard constructs full reasons and JSON evidence.
These timings compare computational policy overhead with differing output work, not equivalent
database implementations. Very short baseline timings are timer/optimizer sensitive and should
not be promoted as credible production throughput or speedup figures.

## Reproduce

```sh
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build build-release -j 2
python3 scripts/run-benchmarks.py
```

The runner uses new temporary database paths, checks command exit status, and writes reports
only after successful parsing and final invariants. The harness accepts up to 1,000,000 events;
that largest size has not run. See data/synthetic for a separate Python snapshot generator.

## Profiling

A GCC -pg build ran the 10,000-event workload on repository workspace storage. The flat
profile excerpt is reports/profile.txt. JSON allocation/serialization and SQLite SQL parsing
and VDBE execution appear among CPU samples. gprof sampling and threaded call counts are
approximate, and do not measure time blocked in storage flushes or SQLite locks. Profiling
is separate from the uninstrumented Release throughput runs. Prepared-statement caching is
a plausible next experiment; it has not been implemented or claimed as an optimization.

```sh
cmake -S . -B build-profile -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF \
  -DCMAKE_CXX_FLAGS=-pg -DCMAKE_EXE_LINKER_FLAGS=-pg
cmake --build build-profile --target stockguard_benchmark -j 2
mkdir -p .runtime
cd .runtime
../build-profile/stockguard_benchmark 10000 fresh-profile.db 1 > profile.json
gprof -b -p ../build-profile/stockguard_benchmark gmon.out > profile-full.txt
```

Only use a new database path. Initial measurements against the old SQLite package were
superseded after upstream research identified the WAL-reset issue. Final checked-in JSON
reports all identify SQLite 3.54.0. There is no claim that a source upgrade improved performance.

## Repeated repository-storage measurements

A follow-up runs the same unchanged Release executable on the repository workspace's
`.runtime` directory, rather than tmpfs. Each of three runs processes 10,000 accepted
observations with one worker, a new database and FULL synchronous transactions.
Reports preserve a shared run ID, per-run latency, binary SHA256, actual CMake build flags
and the observed filesystem type (overlayfs). After the native process closes, the runner
opens each database read-only and requires SQLite integrity_check=ok, zero foreign-key
violations, 10,000 observation rows, 10,001 audit rows, one inventory record at quantity
100 and version 10,001. Verification time is outside the timed native ingestion interval.

Observed throughput: 1,817.7 to 2,011.4 observations/s,
with median 2,001.7. Raw results are in reports/persistent.
These three runs show variability; they are not a confidence interval or a capacity SLA.
Overlay storage and the cloud host's flush behavior do not prove physical power-loss
resilience. The previous tmpfs measurements remain a separate experiment. The executable
is unchanged, so storage and run conditions must not be reported as a code optimization.

```sh
mkdir -p .runtime
python3 scripts/run-benchmarks.py --counts 10000 --workers 1 --repeats 3 \
  --storage-directory .runtime --output reports/persistent
```

`--counts` chooses serial sizes. `--workers` chooses additional 10,000-observation
concurrency configurations. `--repeats` runs each configuration independently, up to 20.
Omitting `--storage-directory` uses system temporary storage. Output files are atomically
replaced only after the corresponding process and database checks succeed; summary.json
is written after all selected runs finish. Check the run ID and process exit code to avoid
mistaking a prior summary for a failed new experiment. Existing records can be retained by
choosing a new output directory. The runner uses Python's SQLite reader only after native
writers close, in read-only mode, to independently inspect standard tables and invariants.

Two reporting regression tests verify that nonzero process exits and successful-looking
JSON without a real persisted database cannot create successful reports. A real 100-event
run also verified this reporting path. No assertions or durability options were disabled.
